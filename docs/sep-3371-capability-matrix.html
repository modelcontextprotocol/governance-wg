How the cells were derived
  • Rows: every L4 outcome in the SEP-3371 capability hierarchy, grouped under its L1, L2 and L3.
  • Cells: inherited from the capability row the group maps to in the matrix sheet. A leaf does not claim a separate assessment.
  • Coarse ratings: Appendix A assessed all ten SDKs on 2026-09-18 for public-API presence.
  • Detailed ratings: Appendix D assessed six SDKs on 2026-10-07. Ruby, PHP, Kotlin and Swift show ? where only the coarse rating exists or no assessment was made.
  • Direction: Partial often means one direction only; hover the cell for the SDK-specific caveat.
  • Roll-up: L1–L3 views aggregate descendants by worst case; click a row to drill down and the breadcrumb to roll back. The top board counts the currently visible level.
  • Cell proof: clicking a status cell opens its claim, the inherited assessment basis, and copyable verification and feature-branch prompts. Each prompt walks up from the target through its L1–L3 ancestors and the required extension point before the target behavior. Nothing is cloned or executed.
  • Not conformance: a ✓ cell can still miss a requirement the row does not isolate. The source matrix and hierarchy live in .workspace-docs/capability-sep-template.md.

The decomposition we would have used

  1. Conceptual agreement. A direction request states the outcome and the non-goals on one page: SDKs need language-agnostic extension points; packaging and stability follow each SDK's policy. No normative text, no tiering.
  2. One SEP for the agreed concept. Semantics and boundaries: what an extension point is, what it must not do, what it must never add to the wire.
  3. One SEP per capability. Registration and dependencies · custom methods · interception (message, then transport) · routes and launch. Each is sponsored, reviewed and landable on its own.
  4. Tracking issues in each SDK. typescript-sdk, python-sdk, go-sdk, csharp-sdk, … each with its own acceptance and sequencing, instead of one MUST set over ten SDKs in a single review.

Counterfactual, stated as such: with the split, registration and dependencies could have reached review without middleware ordering and transport hooks in the same document; a capability missing from one SDK could have been scoped to the SDKs that offer it instead of constraining the shared text; and an extension that shipped early would have had a stable registration target before merge. The SEP may still land as written; the claim is about the order, not the content.
